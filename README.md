## 検索APIのカテゴリー指定

`GET /api/search` は `categories=食品&categories=飲料` の繰り返しクエリで、いずれかのカテゴリーに該当する商品を検索できます。キーワード・価格・在庫条件とはANDで組み合わせます。

- `categories` と `category` がともに未指定・空文字のみの場合は、カテゴリーの絞り込みを行いません。
- 従来の `category=食品` も使用できます。
- 空文字以外の `categories` がある場合は、`category` より優先します。
- 該当件数 `total` は取得上限 `limit` によらず、全該当件数を返します。

検索APIのテストは、リポジトリ直下で次を実行します。FastAPIとhttpxが必要です。環境変数ファイルや実DBは使用せず、SQLiteのインメモリDBで検証します。

```powershell
python -B -m unittest discover -s backend/tests -v
```

## 検索結果の並び替え（STEP 2-2 A〜C）

`GET /api/search` の既存条件とレスポンス `{ total, results }` は維持します。
並び替えは取得上限を適用する前にDBで行います。件数はランキング用JOINの影響を受けません。

| パラメーター | 値 | 意味 |
| --- | --- | --- |
| `sort` | `price_asc` | 価格昇順。同価格は評価済み優先→ベイズ評価降順→有効口コミ件数降順→商品ID昇順 |
| `sort` | `popular` | 指定期間の購入数量合計降順、同数量は商品ID昇順 |
| `sort` | `rating` | 有効口コミから計算するベイズ評価順 |
| `sort` | `recommend` | 送別おすすめ検索。ポリシー一致→未付与→反対、グループ内はスコア降順→商品ID昇順 |
| `gift_policy` | `classic` / `unique` | おすすめ検索では必須。シンプル検索では送信しない |
| `sort` | 未指定 | 互換性のため従来の `sales_count DESC, product_id ASC` |
| `popularity_period` | `weekly` / `monthly` / `yearly` / `all` | 人気順の期間。既定値は `monthly` |
| `scene` | 送別・誕生日・母の日・お歳暮・お中元・結婚祝い・父の日・出産祝い | 同名のproduct_scenes.scene_tagで絞り込み。空・未指定は全シーン |

不正なsort・期間は422を返します。期間は人気順以外では並び順に使いません。
通常検索UIは `sort=popular&popularity_period=monthly` を明示して送ります。
旧APIの個包装・価格帯パラメーターは互換性のため維持します。取引先専用タブ・フォームは画面から撤去しました。

### 人気順の期間と基準日

人気度は `orders.order_id = order_items.order_id` で結合し、
`order_items.product_id` ごとに集計した **`SUM(order_items.quantity)`** です。
注文件数ではありません。販売実績のない商品は数量0として残します。
キャンセル・返品ステータスがないため、その除外処理は行いません。

デモ基準日は `backend/ranking_config.py` の `DEMO_REFERENCE_DATE = date(2026, 6, 30)` です。
検索の購入実績集計と、商品詳細の直近1年購入数量で共用します。
システム日付は変更せず、人気順とおすすめ検索の購入実績集計に使用します。
本番で当日に追従させる際は、タイムゾーンを決めたうえで基準日の取得を
リクエスト時の現在日付へ切り替えてください。APIから任意の日付は指定できません。

| UI | 内部値 | ordered_atの開始（以上） | 終了（未満） |
| --- | --- | --- | --- |
| 週間 | `weekly` | 2026-06-24 00:00:00 | 2026-07-01 00:00:00 |
| 月間 | `monthly` | 2026-06-01 00:00:00 | 2026-07-01 00:00:00 |
| 年間 | `yearly` | 2026-01-01 00:00:00 | 2026-07-01 00:00:00 |
| 全期間（累計） | `all` | 制限なし | 制限なし |

月間は暦月、年間は暦年です。直近30日・365日の定義ではありません。
終了日の翌日未満で比較し、6月30日の注文をすべて含めます。
DATETIMEの保存時刻をそのまま比較するため、日付境界は保存データの時刻基準に従います。

### 価格順の同価格時の扱い

価格を最優先し、同価格の商品の間だけ評価済みを優先します。
続いてベイズ評価スコア降順、有効口コミ件数降順、商品ID昇順で表示します。
未評価商品が安い場合は、高い評価済み商品より前に表示します。
評価済み判定・スコア・件数は以下の評価順と同じ集計を共用し、
`products.rating`・`products.review_count` は順位計算に使いません。
価格順も有効口コミの集計が必要になるため、従来の価格だけのソートより処理量が増えます。
評価集計のSQLは共用し、人気順・sort未指定時には実行しません。

### ベイズ平均による評価順

`score = (v × R + m × C) / (v + m)`、補正係数は `BAYES_PRIOR_WEIGHT = 10` です。

- 有効口コミ：`reviews.rating BETWEEN 1 AND 5` かつ既存商品に紐付くもの。
- v：商品別の有効口コミ件数、R：商品別の有効口コミ平均。
- C：全既存商品の有効口コミをまとめた平均。検索条件や在庫では限定しません。
- Cはリクエスト時に集計し、調査時の4.2021を固定値として使いません。
- 評価済みを優先し、スコア降順→有効口コミ件数降順→商品ID昇順で表示します。
- NULL・範囲外評価は集計から除外し、未評価商品は末尾に商品ID昇順で表示します。
- 全体に有効口コミがない場合も商品を除外せず、商品ID昇順になります。

m=10はgiftia_t105の実データ調査後に採用した値です。
調査時の商品数8,000、有効口コミ24,752、評価済み商品4,296、0件商品3,704、
件数中央値1件、1〜5件商品3,358という分布を踏まえ、少件数商品の過大評価を抑えます。
商品テーブルとの件数不一致1商品・平均不一致1,265商品も確認されているため、
ランキングには `products.rating`・`products.review_count` を使いません。
カード・商品詳細に表示する従来の評価値は変更せず、保存データの補正も行いません。

### フロントエンドの動作

- 初回は検索ボタンで取得し、その後の並び替え・期間変更で直前の検索条件を保持して再検索します。
- フォームの未適用の編集は、自動再検索に含めません。反映には検索ボタンを押します。
- 連続リクエストは最新の結果だけを表示します。
- 条件クリアで月間人気順へ戻し、自動再検索用の条件もクリアします。
- シンプル検索の並び替えは人気順・評価順・価格順です。おすすめ順は候補に含めず、新着順は準備中として選択不可です。
- おすすめ検索は送別シーン・王道／ユニークの指定で実行できます。他のシーンは今後対応予定です。
- シーンは実DBで同名タグを確認した8種類に対応します。好み・年代・性別は両モードでデモ用属性による絞り込みに対応します（STEP C参照）。

## STEP B-4・B-5：送別のおすすめ検索

`GET /api/search?sort=recommend&scene=送別&gift_policy=classic` を使用します。
`gift_policy=unique` に切り替えるとユニーク商品が優先されます。
送別以外・シーン未指定・ポリシー未指定や不正値は422です。
`sort=recommend` はシンプル検索の並び替えには含めません。

### 候補と表示順

在庫あり（`stock > 0`）かつ `product_scenes.scene_tag='送別'` の商品に、
既存のキーワード・カテゴリーOR・価格・個包装条件をANDで適用します。
件数取得と商品取得は共通のWHERE条件を使い、タグ重複でも商品は増えません。

表示順は **ポリシー一致→未付与→反対** です。グループ内のみスコア降順、同点は商品ID昇順です。
合計点が高くても、異なるグループの優先順は逆転しません。
SQLのORDER BYは固定の商品ID順で、全候補取得後にPythonでグループ・スコア・IDを比較します。
DBで先にLIMITしないため、購入実績が少ない一致商品も正しく優先できます。
取得上限はこの順位決定後に適用します。既存のシンプル検索のORDER BY許可リストは維持します。

### スコアとデータ

- シーン対応：30点。
- ポリシー：一致20点、未付与10点、反対0点。
- 購入点：`30 * ln(1+数量) / ln(1+最大数量)`。最大数量0なら0点。
- 口コミ点：`20 * (B-1) / 4`。
- `B = (有効口コミの評価合計 + 10*C) / (有効口コミ件数 + 10)`。

購入数量は `orders.gift_purpose='送別'`、`ordered_at < '2026-07-01'` の注文から
`order_items.quantity` を合計します。estimated_sceneは使いません。
最大数量はフィルターや在庫に限定せず、既存商品全体の送別購入数量から計算します。
CSV事前調査時の最大は779個ですが、実装では固定しません。
有効口コミ・Cは既存の評価順と同じ集計SQLを共用し、検索条件に限定しません。
口コミ0件でもB=Cとして残します。全体に有効口コミがない場合の口コミ点は0点です。
商品カード・詳細画面に表示する通常の評価値は変更しません。

### デモ属性と理由

`backend/data/demo_product_attributes.json` に承認済み40商品（王道20・ユニーク20）を保存しています。
ユニーク4件の差し替え（G0060・G0125・G0005・G0349）も反映済みです。
商品ID・送別シーン・ポリシー・理由・説明文の根拠・`source=demo_curated`を記録しています。
販売数量や口コミで属性を決めたものではありません。既存MySQLは変更しません。

おすすめ結果にだけ `recommendation` を追加し、グループ・総合点・内訳・購入数量・
有効口コミ件数・補正評価・最大2件の理由を返します。
理由は商品の特徴（最大1件）→購入実績（最大1件）の順です。シーン対応・口コミ評価は理由に含めません。
商品の特徴はポリシーの一致・不一致にかかわらず、登録された紹介文がある場合に表示します。
購入実績の集計・期間・数量が1以上という表示条件は維持します。理由が両方ない場合は欄全体を非表示にします。
理由には `kind=feature/purchase` と従来の出典 `database/demo_curated` を保持します。
画面のラベルは「商品の特徴」「購入実績」とし、デモ用紹介文の注記は表示しません。内部の出典情報は維持します。
内部のポリシー状態は保持しますが、カード上の「ポリシー一致／未付与／反対」は表示しません。
ランキング・ベイズ補正・通常の評価表示は変更しません。旧保存結果のkindがない理由は非表示になります。
未評価・購入実績なしの商品に架空の理由を付けません。年代・性別・好みはスコア・理由に使いません。

## 商品詳細の直近1年購入数量

商品詳細APIは、`orders` と `order_items` を `order_id` で結合し、対象商品の
`SUM(quantity)` を `recent_year_sales_count` として返します。注文件数・購入者数ではありません。
注文目的による限定はせず、デモ基準日を含む直近1暦年を対象にします。
現在は `2025-07-01 <= ordered_at < 2026-07-01` で、6月30日の日時をすべて含めます。
開始日は基準日の翌日から1暦年前（応当日がなければその月末）です。
`sales_period_start` と `sales_period_end`（末日を含む）も返し、画面には対象期間を併記します。
0件時は従来どおり購入実績を非表示にし、保存値への代替表示はしません。
従来の `sales_count` は互換性のため保持し、検索ランキング・類似商品・口コミは変更しません。
商品と属性の取得と同じ `db_cursor` を利用します。DBのスキーマ・データは変更しません。
キャンセル・返品の状態が現在のDBにないため、除外集計は行いません。
バックエンドの `test_product_sales.py` とフロントエンドの `product-sales.test.mjs` で
期間境界・数量集計・0件・表示期間・保存値を使わないことを検証します。

## STEP C：受取人の年代・性別・好みによる絞り込み

画面上のモード名は「おまかせで探す」（おすすめ検索）と「自分で探す」（シンプル検索）です。
各ボタンの左にSparkles／SlidersHorizontalのSVGアイコンを配置しています。
選択中は濃いネイビー背景・白文字と白アイコン、未選択は白背景・ブルーグレー枠・ネイビー文字とアイコンです。
既存のコンパクトな横並び・角丸・スマートフォン向けサイズを維持しています。
タグ下の補足説明とギフトポリシー未選択時の案内文は省略し、年代・性別は「任意」と表示します。
デモ属性データ・検索条件・必須入力の制御は変更していません。

おすすめ検索・シンプル検索の共通条件として、次の任意パラメーターを追加しています。
既存のパラメーターとレスポンス `{ total, results }` は維持します。

| パラメーター | 値 | 条件 |
|---|---|---|
| `target_age` | 20代・30代・40代・50代・60代以上 | 単一選択 |
| `target_gender` | 男性・女性 | 単一選択 |
| `preferences` | 既存UIの好みの内部ID | 繰り返し指定はOR |

例：`/api/search?scene=送別&target_age=30代&target_gender=女性&preferences=coffee-tea&preferences=gourmet`

年代・性別は省略・空文字・「指定なし」で絞り込みません。好みは省略で絞り込みません。
不正値は422です。年代・性別・好み・既存フィルター間はANDです。
年代と性別の両方を指定した場合は、**同じ登録ペア**で一致する必要があります。
属性未登録の商品は指定した属性に一致しません。全属性未指定ならJSON登録外の商品も対象です。
「その他」は通常の好みであり、未分類商品の受け皿にはしていません。
0件なら0件と条件解除の案内を表示し、自動で条件を緩和しません。

### 属性データと移行

`backend/data/demo_recipient_attributes.json` は商品IDをキーとする152商品のデモ属性です。
承認済み150商品に、商品名に明確な根拠があるG0034（花と菓子：植物・花／グルメ）と
G5157（レストラン体験：グルメ）を追加しました。STEP Bの40商品のうち33商品を含みます。
残る7商品は無理に分類せず、年代・性別の根拠がない商品には好みだけを登録しています。
年代・性別は受取人を明示する商品説明の記載を使用し、購入者の属性は流用していません。
属性は検索候補のデモ用分類であり、その年代・性別の全員に適すると保証するものではありません。

- `products[商品ID].targets`：`target_age`・`target_gender`・引用根拠をペアごとに保持。
  `product_targets(product_id, target_age, target_gender)` へ移行できる構造です。
  別のペアを組み合わせて架空の対象を作りません。
- `preferences`：16種類のUI内部IDの配列。`preference_evidence` に出典フィールド・引用・分類理由を保持。
- `source=demo_curated`：実DBの商品属性と区別します。価格・在庫・実績・評価はJSONで上書きしません。
- `preference_master`：UI内部IDと表示名を保持。DBマスタIDは未確定のため `db_preference_tag_id=null`。
  SQL定義のPT001「シンプル」等は、実DBマスタの確認後に対応を確定してください。
  「甘い」と「グルメ」等の異なる概念を自動で同一視せず、`preference_tags` と
  `product_preference` への移行時もAPIの内部IDを維持します。

JSONの読み込み・照合は `backend/recipient_attributes.py` に独立しています。
一致IDをプレースホルダーで共通WHEREに追加し、件数・商品取得の両方に適用します。
一致なしは `1 = 0`。全候補を絞り込んでから既存ランキングと件数制限を適用するため、
上位20件だけの事後フィルターにはなりません。
STEP Bのグループ順・購入点・口コミ点・理由は変更せず、正規化の母集団も維持しています。
既存の `demo_product_attributes.json` は変更していません。

### 制約と確認方法

今回のデータは送別CSVを出典としており、他シーンでの網羅性は未確認です。
旅行・お酒・おしゃれ・料理・その他は根拠のある登録がなく、単独指定では0件です。
複合条件でも0件になる組み合わせがあります。検索UIには0件時の条件解除の案内を表示します。
データ追加時も、根拠のない属性や全年代・全性別の一括付与はしないでください。


画面では両モードで属性を選び、条件クリア、好みの展開・折りたたみ、並び替え、
